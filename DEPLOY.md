# Deploying Quizora

Target architecture:

```
Browser ──► Vercel (React static build)  ──HTTPS + Bearer token──►  Render (Spring Boot Docker)
                                                                          │
                                                                          └──TLS──► Aiven (MySQL)
```

Three separate accounts are involved, and every step below is done in a browser by you —
no cloud CLI is installed on this machine and no credentials are stored in the repo.

Order matters: **Aiven → Render → Vercel → update Render CORS → verify.**

---

## 1. Aiven — managed MySQL

1. Sign up at <https://aiven.io> and create a service:
   - **Service type:** MySQL
   - **Plan:** Free
   - **Cloud/region:** the one closest to you (Render's free region is Oregon; either works,
     latency is not critical for this app)
2. Wait until the service state is **Running**, then open its **Overview** page and copy the
   **Service URI**. It looks like:

   ```
   mysql://avnadmin:PASSWORD@mysql-xxxx.aivencloud.com:25060/defaultdb?ssl-mode=REQUIRED
   ```

3. Convert it to the three values the backend expects:

   | Render env var | Value |
   |---|---|
   | `DB_URL` | `jdbc:mysql://mysql-xxxx.aivencloud.com:25060/defaultdb?ssl-mode=REQUIRED&serverTimezone=UTC` |
   | `DB_USERNAME` | `avnadmin` |
   | `DB_PASSWORD` | the password from the URI (URL-encoded if it contains `@ : / ?`) |

   Notes:
   - Keep the `jdbc:` prefix and the **exact port** (Aiven does not use 3306).
   - `ssl-mode=REQUIRED` encrypts the connection. Aiven's CA can be pinned with
     `ssl-mode=VERIFY_IDENTITY`, but that needs the CA in a JVM truststore — optional for a
     course project.
   - `defaultdb` already exists; Hibernate creates the tables on first start
     (`ddl-auto=update`). Do not create a schema by hand.
   - If the connection hangs, check Aiven's **Allowed IP addresses** setting; the default
     allows public access, which is what Render needs.

---

## 2. Render — the API

The repo already contains [`render.yaml`](../render.yaml) and
[`backend/Dockerfile`](../backend/Dockerfile).

1. Push the repository to GitHub (the existing `origin` remote is fine).
2. In Render: **New +** → **Blueprint** → select the repo → **Apply**.
   Render reads `render.yaml` and creates the `quizora-api` web service (Docker, free plan,
   health check on `/api/courses`).
3. Fill the values marked `sync: false`:

   | Variable | Value |
   |---|---|
   | `DB_URL` | from step 1 |
   | `DB_USERNAME` | from step 1 |
   | `DB_PASSWORD` | from step 1 |
   | `CORS_ALLOWED_ORIGINS` | `https://placeholder.vercel.app` for now — replaced in step 4 |
   | `SEED_TEACHER_PASSWORD` | **set this now**, e.g. a 16+ character password |

   `JWT_SECRET` is generated by Render automatically (`generateValue: true`) and persists
   across deploys. `SPRING_PROFILES_ACTIVE=mysql` is already set by the blueprint.

4. Deploy. Watch the logs for:
   - `Seeded demo accounts: … (TEACHER), … (STUDENT)` — first boot only
   - `Started QuizPlatformApplication`
   - No `Communications link failure` (that means `DB_URL`/TLS is wrong)

5. Copy the service URL, e.g. `https://quizora-api.onrender.com`, and check:

   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' https://quizora-api.onrender.com/api/courses   # 200
   ```

   Free instances sleep after ~15 minutes idle; the first request after that can take
   30–60 seconds. The frontend waits up to 45 seconds for a response.

---

## 3. Vercel — the frontend

1. Vercel: **Add New…** → **Project** → import the same GitHub repo.
2. Settings that matter:
   - **Root Directory:** `frontend` ← required, otherwise Vercel builds the repo root
   - **Framework Preset:** Vite (detected from `frontend/vercel.json`)
   - **Build Command:** `npm run build`
   - **Output Directory:** `dist`
   - **Install Command:** `npm ci`
   - **Environment Variable:** `VITE_API_BASE` = `https://quizora-api.onrender.com`

   Optional: `VITE_SHOW_DEMO_CREDENTIALS=true` shows the demo-account hints on the login
   page. They are hidden in production by default, because a public URL should not advertise
   credentials — and because they would be wrong anyway once you change
   `SEED_TEACHER_PASSWORD`.

   `VITE_API_BASE` is baked into the bundle at **build time**. Changing it later requires a
   redeploy, not just a settings change. Leave it unset for local development: the Vite proxy
   then forwards `/api` to `localhost:8080`.

3. Deploy and open the `*.vercel.app` URL.

---

## 4. Connect the two origins (the step people forget)

The browser calls Render from the Vercel origin, so Render must allow it:

1. In Render → `quizora-api` → **Environment**, set:

   ```
   CORS_ALLOWED_ORIGINS=https://your-app.vercel.app,https://*.vercel.app
   ```

   - List the production URL explicitly.
   - `https://*.vercel.app` additionally covers preview deployments. It is broader than
     necessary; drop it if you only use production.
   - No wildcard for the scheme/host beyond that, and `allowCredentials` stays off because
     auth uses the `Authorization` header, not cookies.

2. **Manual Deploy → Deploy latest commit** (or restart) so the new environment is picked up.
3. Hard-refresh the Vercel site. If you see `Failed to fetch` / a CORS error in the console,
   the origin string does not match exactly — `https://` and no trailing slash.

---

## 5. Verify the deployment

```bash
API=https://quizora-api.onrender.com

# 1. Catalogue is public
curl -s -o /dev/null -w 'courses: %{http_code}\n' $API/api/courses

# 2. Login works (use the password you set in SEED_TEACHER_PASSWORD)
curl -s -X POST $API/api/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"teacher@quizora.local","password":"YOUR-TEACHER-PASSWORD"}' \
  | head -c 120; echo

# 3. Preflight from the Vercel origin is allowed
curl -s -i -X OPTIONS $API/api/auth/login \
  -H 'Origin: https://your-app.vercel.app' \
  -H 'Access-Control-Request-Method: POST' \
  -H 'Access-Control-Request-Headers: content-type' | head -12
```

Then in the browser on the Vercel URL:

1. Log in as the teacher → **Dashboard** shows the two seeded/attempt rows area and topic stats.
2. Log out, register a student, take a quiz in **Java Programming → Basics**, submit.
3. **My attempts** lists the attempt; opening it replays the saved review.
4. Log back in as the teacher → the student's attempt appears; clicking it opens their review.

## Operations

**Rotate the teacher password.** The seeder only runs on an empty `app_users` table, so
changing `SEED_TEACHER_PASSWORD` later has no effect. Either create the account again by
wiping `app_users` (destroys attempts via the FK — avoid), or register a second teacher with
a one-off SQL statement using a BCrypt hash:

```sql
-- generate the hash with: htpasswd -bnBC 10 "" 'new-password' | tr -d ':\n' | sed 's/$2y/$2a/'
INSERT INTO app_users (email, name, password_hash, role, created_at)
VALUES ('you@example.com', 'Your Name', '$2a$10$…', 'TEACHER', NOW());
```

**Redeploys.** `autoDeploy: true` means every push to the default branch rebuilds the API.
The frontend rebuilds on push as well. MySQL data is unaffected by either.

**Logs and health.**
- Render → Logs (structured Spring output).
- Health check path: `/api/courses` (no auth required, touches the database).
- Locally: `http://localhost:8080/h2-console` remains available on the H2 profile only.

**Cost.** Aiven MySQL free, Render free (sleeps when idle), Vercel Hobby. No paid resource is
required for this project.

## Local production rehearsal (optional)

```bash
# Backend with the MySQL profile against any reachable MySQL
cd backend
DB_URL='jdbc:mysql://HOST:PORT/defaultdb?ssl-mode=REQUIRED&serverTimezone=UTC' \
DB_USERNAME=avnadmin DB_PASSWORD='…' \
JWT_SECRET='a-48-character-minimum-secret-for-hs384-signing-000' \
CORS_ALLOWED_ORIGINS='http://localhost:4173' \
./mvnw spring-boot:run -Dspring-boot.run.profiles=mysql

# Frontend built exactly like Vercel does
cd frontend
VITE_API_BASE=http://localhost:8080 npm run build && npx vite preview --port 4173
```

`vite preview` still uses the dev proxy, so `VITE_API_BASE` can also stay unset locally.
